# Конституция проекта

Версия: 1.0

Статус: Действует

---

# 1. Назначение

Настоящий документ определяет обязательные правила разработки проекта.

Все остальные стандарты, архитектурные решения (ADR), правила и инструкции не могут противоречить настоящему документу.

---

# 2. Основные цели проекта

Проект предназначен для создания единой системы инвентаризации ИТ-инфраструктуры предприятия.

Архитектура проекта должна обеспечивать:

- масштабируемость;
- сопровождаемость;
- минимальную связанность компонентов;
- возможность расширения без изменения существующего кода.

---

# 3. Основные принципы разработки

Обязательными являются следующие принципы.

## 3.1. Отсутствие предположений

Запрещается:

- придумывать отсутствующий код;
- придумывать отсутствующие поля БД;
- придумывать отсутствующие таблицы;
- придумывать отсутствующие API;
- придумывать отсутствующие классы;
- делать выводы при отсутствии информации.

При недостатке информации необходимо запросить соответствующий код.

---

## 3.2. Минимальный шаг разработки

Любое изменение выполняется небольшими этапами.

Каждый этап включает:

1. обсуждение;
2. согласование;
3. генерацию изменений;
4. проверку;
5. исправление (при необходимости);
6. повторную проверку;
7. коммит.

Запрещается выполнять несколько крупных рефакторингов одновременно.

---

## 3.3. Рабочий код

Любой генерируемый код должен быть готов к непосредственной вставке в проект.

Запрещается использовать:

- ...
- остальной код без изменений
- аналогично
- и т.д.

При изменении метода генерируется полная версия метода.

При изменении класса генерируется полный класс.

---

# 4. Работа с базой данных

Структура базы данных считается эталоном проекта.

Запрещается:

- самостоятельно изменять структуру БД;
- придумывать поля;
- придумывать таблицы;
- изменять типы данных без согласования.

Любые изменения структуры БД предварительно обсуждаются.

После согласования создаётся миграция.

---

# 5. Архитектурные изменения

Любое изменение архитектуры предварительно обсуждается.

После согласования оформляется соответствующий ADR.

После реализации ADR переводится в состояние "Реализовано".

---

# 6. Документирование

Документирование является обязательной частью разработки.

В проекте используются следующие виды документов:

- стандарты проекта;
- архитектурные решения (ADR);
- техническая документация;
- комментарии к коду.

---

# 7. Стандарты проекта

Обязательными являются следующие стандарты:

- 01-role-ai.md
- 02-development-environment.md
- 03-working-protocol.md
- 04-output-standard.md
- 05-adr-standard.md

Все стандарты являются нормативными документами проекта.

---

# 8. Архитектурные решения (ADR)

Все архитектурные решения оформляются отдельными документами.

ADR описывает:

- проблему;
- причины;
- принятое решение;
- последствия;
- влияние на проект.

Порядок ведения ADR определяется документом:

05-adr-standard.md

---

# 9. Подсистема Output

Во всём проекте используется единая подсистема Output.

Запрещается использовать напрямую:

- echo
- print
- printf
- stdout
- stderr
- Yii::info()
- Yii::warning()
- Yii::error()

Все сообщения выводятся исключительно через OutputInterface.

---

# 10. Ответственность

## Архитектор (ИИ)

Отвечает за:

- архитектуру;
- проектирование;
- рефакторинг;
- подготовку ADR;
- поддержание единого архитектурного стиля.

## Разработчик

Отвечает за:

- внедрение изменений;
- проверку работоспособности;
- сохранение документов;
- выполнение коммитов;
- принятие архитектурных решений совместно с архитектором.

---

# 11. Приоритет документов

Приоритет документов проекта следующий:

1. Конституция проекта
2. Стандарты проекта
3. ADR
4. Техническая документация
5. Исходный код

Документ более высокого уровня имеет приоритет над документом более низкого уровня.

---

# 12. Изменение Конституции

Изменение настоящего документа допускается только после обсуждения и совместного согласования архитектором и разработчиком.

Каждое изменение должно быть отражено в журнале изменений проекта.
