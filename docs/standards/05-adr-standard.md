# Стандарт проекта
# Architecture Decision Records (ADR)

Версия: 1.0

Статус: Действует

---

# 1. Назначение

Architecture Decision Record (ADR) — документ, фиксирующий принятое архитектурное решение.

ADR отвечает на вопрос:

> Почему архитектура проекта устроена именно так?

ADR не является технической документацией, пользовательской инструкцией или описанием реализации.

---

# 2. Цели использования ADR

Использование ADR обеспечивает:

- сохранение истории архитектуры;
- понимание причин принятых решений;
- снижение риска повторного обсуждения уже решённых вопросов;
- сопровождение проекта спустя длительное время;
- единый стиль развития архитектуры.

---

# 3. Когда создаётся ADR

ADR создаётся только для архитектурных решений.

Например:

- введение новой подсистемы;
- изменение архитектуры взаимодействия компонентов;
- переход на новую модель проектирования;
- введение нового архитектурного стандарта;
- изменение принципов взаимодействия сервисов;
- изменение общей структуры проекта.

---

# 4. Когда ADR НЕ создаётся

ADR не создаётся для:

- исправления ошибок;
- небольших рефакторингов;
- переименования методов;
- оптимизации SQL;
- изменения оформления кода;
- изменения комментариев;
- исправления опечаток;
- обновления зависимостей.

---

# 5. Авторство

Автором всех ADR является ИИ.

Разработчик:

- рассматривает документ;
- согласовывает;
- сохраняет файл;
- выполняет коммит.

---

# 6. Нумерация

Используется последовательная нумерация.

Примеры:

```
ADR-0000.md
ADR-0001.md
ADR-0002.md
ADR-0003.md
```

Номера повторно не используются.

---

# 7. Размещение

Все ADR размещаются в каталоге:

```
docs/architecture/
```

---

# 8. Структура ADR

Каждый ADR содержит следующие разделы.

```
Название

Статус

Дата

---

Проблема

Контекст

Рассмотренные варианты

Принятое решение

Последствия

Влияние на проект

Связанные ADR

Статус реализации
```

Допускается добавление дополнительных разделов при необходимости.

---

# 9. Статусы ADR

Поддерживаются следующие статусы.

```
Proposed
```

Предложено.

---

```
Accepted
```

Принято.

---

```
Implemented
```

Полностью реализовано.

---

```
Deprecated
```

Устарело.

---

```
Superseded
```

Заменено другим ADR.

---

```
Rejected
```

Отклонено.

---

# 10. Статус реализации

Каждый ADR должен содержать информацию о реализации.

Например:

```
Не начато
```

или

```
В процессе
```

или

```
Реализовано
```

При возможности рекомендуется указывать коммит, завершивший реализацию.

Например:

```
Реализовано.

Коммит:

4b91a63
```

---

# 11. Изменение ADR

После получения статуса **Accepted** текст ADR изменяться не должен.

Допускается изменение только следующих разделов:

- Статус;
- Статус реализации;
- Связанные ADR.

Если архитектурное решение изменилось, создаётся новый ADR.

---

# 12. Связанные ADR

Если новое решение основано на предыдущем, необходимо добавить ссылки.

Например:

```
Связанные ADR

ADR-0001

ADR-0003
```

---

# 13. Принцип неизменности

ADR является историческим документом.

Он отражает состояние архитектуры на момент принятия решения.

Историческая часть ADR не переписывается.

---

# 14. Ответственность

ИИ обязан:

- определить необходимость создания ADR;
- подготовить документ;
- обеспечить единый стиль оформления;
- проверить отсутствие противоречий;
- предложить обновление статусов ранее созданных ADR.

---

# 15. Жизненный цикл ADR

```
Обнаружение архитектурной проблемы
                │
                ▼
Обсуждение
                │
                ▼
Согласование
                │
                ▼
Создание ADR
                │
                ▼
Принятие решения
                │
                ▼
Реализация
                │
                ▼
Проверка
                │
                ▼
Коммит
                │
                ▼
Изменение статуса ADR
```

---

# 16. Обязательность

Все значимые архитектурные изменения проекта должны сопровождаться соответствующим ADR.

Отсутствие ADR для архитектурного решения считается нарушением архитектурного стандарта проекта.
