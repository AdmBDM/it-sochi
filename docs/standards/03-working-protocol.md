# Стандарт проекта
# Рабочий протокол

Версия: 1.0

Статус: Действует

---

# 1. Назначение

Настоящий документ определяет единый порядок взаимодействия между разработчиком и ИИ при выполнении любых работ над проектом.

Цель протокола — обеспечить предсказуемость разработки, минимизировать количество ошибок и исключить выполнение неподтверждённых изменений.

---

# 2. Общий цикл разработки

Любая задача выполняется по следующей схеме:

```
Постановка задачи
        │
        ▼
Анализ существующей реализации
        │
        ▼
Обсуждение архитектуры
        │
        ▼
Согласование решения
        │
        ▼
Минимальный этап реализации
        │
        ▼
Проверка
        │
        ▼
Исправление (при необходимости)
        │
        ▼
Повторная проверка
        │
        ▼
Коммит
```

Переход к следующему этапу допускается только после успешной проверки предыдущего.

---

# 3. Правило минимального изменения

За один этап допускается изменение только одной логически завершённой части системы.

Например:

- перенос одного метода;
- создание одного сервиса;
- введение одного интерфейса;
- замена одного способа взаимодействия.

Запрещается объединять несколько независимых изменений в один этап.

---

# 4. Обязательное согласование

Перед генерацией кода ИИ обязан:

- сформулировать цель изменения;
- описать предполагаемый результат;
- объяснить влияние на архитектуру (если оно имеется);
- получить подтверждение разработчика.

Без подтверждения реализация не начинается.

---

# 5. Генерация кода

Генерируемый код должен быть полностью готов к использованию.

Запрещается использовать:

- сокращённые версии;
- псевдокод;
- комментарии вида "остальной код без изменений";
- ссылки на отсутствующие части реализации.

При изменении метода генерируется полный метод.

При изменении класса — полный класс.

---

# 6. Проверка

После внедрения каждого изменения разработчик выполняет проверку.

Проверка включает:

- отсутствие синтаксических ошибок;
- успешный запуск;
- проверку изменённого функционала;
- анализ сообщений об ошибках.

При обнаружении ошибки дальнейшие этапы приостанавливаются до её устранения.

---

# 7. Работа с ошибками

Если обнаружена ошибка:

1. фиксируется текст ошибки;
2. определяется причина;
3. устраняется только причина ошибки;
4. выполняется повторная проверка.

Запрещается одновременно исправлять посторонние проблемы.

---

# 8. Работа с архитектурой

Если в процессе реализации обнаружена архитектурная проблема, допускается временная остановка текущего рефакторинга.

Последовательность действий:

1. анализ проблемы;
2. обсуждение;
3. согласование;
4. инфраструктурное изменение;
5. проверка;
6. возврат к основной задаче.

---

# 9. Работа с документацией

Архитектурные изменения сопровождаются:

- обновлением стандартов (при необходимости);
- созданием ADR;
- актуализацией технической документации.

Документация является обязательной частью результата.

---

# 10. Работа с Output

Во всех новых компонентах проекта используется исключительно подсистема Output.

Любой новый сервис должен получать объект OutputInterface через конструктор либо использовать NullOutput по умолчанию.

Прямой вывод сообщений запрещён.

---

# 11. Работа с сервисами

Каждый сервис должен:

- выполнять одну основную задачу;
- иметь минимальное количество зависимостей;
- не обращаться напрямую к пользовательскому интерфейсу;
- не зависеть от контроллеров.

Контроллер отвечает только за организацию выполнения сценария.

---

# 12. Работа с контроллерами

Контроллер:

- получает параметры;
- создаёт необходимые сервисы;
- организует последовательность вызовов;
- выводит результат.

Контроллер не должен содержать бизнес-логику.

---

# 13. Работа с рефакторингом

При выполнении рефакторинга соблюдается следующий порядок:

1. выделение ответственности;
2. создание интерфейса;
3. перенос функциональности;
4. проверка;
5. удаление старой реализации.

Каждый этап завершается отдельной проверкой.

---

# 14. Коммит

После успешного завершения этапа выполняется отдельный коммит.

Один этап — один коммит.

Коммит не должен содержать несвязанные изменения.

---

# 15. Главный принцип

Если существует возможность выполнить изменение проще, безопаснее и меньшим объёмом, предпочтение всегда отдаётся этому варианту.

Надёжность проекта имеет приоритет над скоростью разработки.
