# ADR-0000
# Переход проекта на архитектурное управление посредством ADR

Статус: Accepted

Дата: 2026-07-19

Статус реализации: Implemented

---

# Проблема

По мере развития проекта количество архитектурных решений постоянно увеличивается.

Часть решений принимается в процессе обсуждений, часть — во время рефакторинга, часть — при проектировании новых подсистем.

Без документирования причин принятия этих решений со временем возникают проблемы:

- невозможно быстро восстановить логику развития архитектуры;
- возрастает риск повторного обсуждения уже решённых вопросов;
- ухудшается сопровождаемость проекта;
- усложняется подключение новых разработчиков;
- появляется вероятность принятия решений, противоречащих ранее согласованной архитектуре.

---

# Контекст

Проект перешёл от стадии первоначальной разработки к стадии длительного развития.

В проекте уже появились собственные архитектурные стандарты:

- сервисная архитектура;
- единая подсистема Output;
- поэтапный рефакторинг;
- обязательное документирование архитектуры.

Для дальнейшего развития требуется единый механизм фиксации архитектурных решений.

---

# Рассмотренные варианты

## Вариант 1

Не документировать архитектурные решения.

Недостатки:

- потеря истории проекта;
- зависимость от памяти участников;
- невозможность понять причины существующей архитектуры.

Решение отклонено.

---

## Вариант 2

Вести единый архитектурный документ.

Недостатки:

- документ быстро становится громоздким;
- сложность поиска решений;
- невозможность проследить эволюцию архитектуры.

Решение отклонено.

---

## Вариант 3

Использовать отдельный документ для каждого архитектурного решения (ADR).

Преимущества:

- каждое решение документируется отдельно;
- легко отслеживается история развития проекта;
- отсутствуют конфликты между независимыми решениями;
- обеспечивается масштабируемость документации.

Данный вариант признан оптимальным.

---

# Принятое решение

В проекте вводится обязательное использование **Architecture Decision Records (ADR)**.

Каждое архитектурное решение оформляется отдельным документом.

Все ADR размещаются в каталоге:

```
docs/architecture/
```

Оформление выполняется в соответствии со стандартом:

```
docs/standards/05-adr-standard.md
```

---

# Авторство

Единственным автором ADR является ИИ.

В обязанности ИИ входит:

- определение необходимости создания ADR;
- подготовка текста документа;
- поддержание единого стиля;
- контроль согласованности архитектурных решений;
- актуализация статусов ADR.

Разработчик выполняет:

- рассмотрение документа;
- согласование;
- сохранение файла;
- фиксацию в системе контроля версий.

---

# Правила применения

ADR создаётся исключительно для архитектурных решений.

Исправления ошибок, локальные изменения кода и небольшие рефакторинги ADR не требуют.

---

# Последствия

Положительные:

- появляется полная история развития архитектуры;
- значительно повышается сопровождаемость проекта;
- исключается повторное обсуждение уже принятых решений;
- архитектура становится прозрачной и воспроизводимой.

Отрицательные:

- появляется необходимость сопровождения архитектурной документации.

Указанный недостаток признан несущественным по сравнению с преимуществами.

---

# Влияние на проект

С момента принятия настоящего ADR:

- архитектурные решения документируются обязательно;
- архитектура проекта считается частью документации;
- развитие проекта сопровождается соответствующими ADR.
