# 2. ADR-0002. Архитектура подсистемы справочников
===============================================================================

# ADR-0002

# Архитектура подсистемы справочников

Статус: Accepted

Дата: 2026-07-22

---

# Контекст

Первоначальная структура справочников была разработана для системы инвентаризации оборудования.

По мере развития проекта система постепенно превращается в полноценную CMDB.

В результате существующая архитектура перестала удовлетворять требованиям:

- Discovery должен работать независимо от структуры существующих справочников;
- требуется единая модель хранения мастер-данных;
- необходимо исключить использование отображаемых названий (`name`) в программной логике;
- требуется возможность построения произвольных иерархий;
- существующая пространственная модель не отражает реальные отношения объектов.

---

# Принятые решения

## 1. Вводится единая подсистема мастер-данных.

Все вновь создаваемые справочники проектируются как Master Data.

Новые справочники не должны зависеть от структуры существующих таблиц.

---

## 2. Все программные обращения осуществляются только по полю `code`.

Поле

```
name
```

используется исключительно для отображения пользователю.

Во всех сервисах, Discovery, API, импорте и внутренней логике запрещается использовать `name` для идентификации объектов.

---

## 3. Вводится единый механизм хранения иерархических классификаторов.

Создаётся единая таблица

```
classifiers
```

использующая модель "лес".

Каждый корневой элемент дерева представляет отдельный классификатор.

Пример:

```
device_types
space_object_types
organization_object_types
```

Все остальные записи являются потомками соответствующего дерева.

---

## 4. Все новые классификаторы строятся по единому принципу.

Любой новый классификатор создаётся добавлением нового корневого элемента дерева.

Изменение структуры БД для создания нового классификатора не требуется.

---

## 5. Пространственная модель объединяется.

Существующие сущности

- buildings
- departments
- locations

заменяются единой пространственной моделью.

Пространственные объекты образуют дерево.

Пример:

```
Здание
    Блок
        Этаж
            Помещение
                Рабочее место
```

---

## 6. Организационная модель отделяется от пространственной.

Организационная структура не зависит от расположения объектов.

Организационная модель проектируется отдельно.

Пример:

```
Организация
    Подразделение
        Сектор
```

Связь сотрудников осуществляется с организационной структурой.

Связь рабочих мест осуществляется с пространственной структурой.

---

## 7. Производители и модели разделяются.

Производители оборудования выделяются в самостоятельный справочник

```
vendors
```

Модели оборудования объединяются в единый каталог

```
catalog_items
```

Каталог является иерархическим.

Пример:

```
HP
    LaserJet
        M404dn
```

---

## 8. Все новые деревья используют одинаковую архитектуру.

Любая иерархическая сущность использует одинаковую структуру:

- id
- parent_id
- code
- name

Дополнительные поля определяются только предметной областью.

---

## 9. Обратная совместимость является обязательной.

До завершения рефакторинга старые таблицы продолжают существовать.

Удаление старых сущностей производится только после:

- создания новой структуры;
- переноса данных;
- перевода всех моделей;
- перевода сервисов;
- перевода API;
- перевода Discovery.

---

## 10. Перенос данных осуществляется поэтапно.

При необходимости допускается использование временных полей соответствия.

После завершения миграции временные поля удаляются.

---

## 11. Стандарт новых таблиц.

Все новые сущности используют единый стандарт.

Обязательные поля:

```
id
code
name
sort_order
is_active
created_at
updated_at
```

Иерархические сущности дополнительно содержат

```
parent_id
```

---

## 12. Временные метки.

Во всех новых таблицах используются

```
created_at timestamp default now()

updated_at timestamp default now()
```

Поле

```
updated_at
```

обновляется исключительно триггером

```
update_updated_at_column()
```

Единый триггер используется всеми сущностями проекта.

---

## 13. Типы идентификаторов.

Во всех новых таблицах используется тот же тип идентификаторов, что и в существующей БД.

```
primaryKey()
```

Переход на bigint не производится.

---

## 14. Правила разработки.

После утверждения настоящего ADR:

- архитектура считается зафиксированной;
- любые изменения оформляются новым ADR;
- миграции не имеют права изменять архитектуру;
- миграции обязаны реализовывать утверждённую модель.

---

# Последствия

Подсистема справочников становится независимой от существующей структуры БД.

Discovery получает стабильные программные идентификаторы.

CMDB получает единую модель хранения мастер-данных.

Добавление новых классификаторов не требует изменения структуры БД.

Архитектура становится пригодной для дальнейшего развития API, импорта, Discovery и интеграционных сервисов.

# 3. MDM-0001. Master Data Model
===============================================================================

# MDM-0001

# Master Data Model

Версия: 1.0

Статус: Accepted

Дата: 2026-07-22

---

# Назначение

Настоящий документ определяет единую модель мастер-данных проекта.

Все последующие миграции, модели ActiveRecord, сервисы, Discovery, импорт, API и пользовательский интерфейс обязаны использовать исключительно настоящую модель.

Настоящий документ является основным источником истины для структуры мастер-данных проекта.

---

# Общая модель

Подсистема мастер-данных состоит из пяти основных сущностей.

```
                 classifiers
                      │
                      │
      ┌───────────────┼───────────────┐
      │               │               │
      │               │               │
catalog_items   space_objects   organization_objects
      │
      │
   vendors
```

---

# Сущности

## 1. classifiers

Назначение

Хранение всех иерархических классификаторов проекта.

Особенности

- единая таблица;
- модель хранения "лес";
- каждый классификатор является корневым узлом;
- дочерние элементы образуют дерево.

Примеры корневых узлов

```
device_types

space_object_types

organization_object_types
```

Ответственность

- типы устройств;
- типы пространственных объектов;
- типы организационных объектов;
- будущие классификаторы проекта.

---

## 2. vendors

Назначение

Хранение производителей оборудования.

Примеры

```
HP

Dell

Brother

Kyocera

Cisco

MikroTik
```

Особенности

Справочник является плоским.

Иерархия отсутствует.

---

## 3. catalog_items

Назначение

Единый каталог оборудования.

Особенности

Иерархическая структура.

Типичная схема

```
HP
    LaserJet
        M404dn
        M428fdw

Dell
    OptiPlex
        7090
```

Ответственность

Описание каталога оборудования.

Каталог не содержит конкретных устройств.

---

## 4. space_objects

Назначение

Единая пространственная модель предприятия.

Иерархическая структура.

Типичный пример

```
Здание

    Блок

        Этаж

            Помещение

                Рабочее место
```

Заменяет

```
buildings

departments

locations
```

Ответственность

Описание физических объектов предприятия.

---

## 5. organization_objects

Назначение

Организационная структура предприятия.

Иерархическая структура.

Типичный пример

```
Организация

    Управление

        Отдел

            Сектор
```

Ответственность

Описание организационной структуры.

Не содержит пространственных данных.

---

# Принципы моделирования

---

## Пространственная модель независима

Физическое расположение объектов описывается исключительно

```
space_objects
```

---

## Организационная модель независима

Организационная структура описывается исключительно

```
organization_objects
```

---

## Производители отделены от каталога

Производитель является самостоятельной сущностью.

Каталог оборудования использует ссылку на производителя.

---

## Классификаторы независимы от каталогов

Тип оборудования определяется классификатором.

Каталог оборудования не является классификатором.

---

## Все иерархии используют одинаковую модель

Любая древовидная сущность использует одинаковую архитектуру.

```
parent_id
```

является единственным механизмом построения дерева.

---

# Что не относится к Master Data

Следующие сущности не являются мастер-данными.

```
devices

employees

movements

printer_page_counters

discovered_devices

users

...
```

Они используют Master Data, но не входят в неё.

---

# Общая схема зависимостей

```
classifiers
    │
    ├───────────────┐
    │               │
    │               │
space_objects   organization_objects

vendors
    │
    │
catalog_items

devices
    │
    ├──────────────► catalog_items
    │
    ├──────────────► space_objects
    │
    ├──────────────► organization_objects
    │
    └──────────────► classifiers
```

---

# Правила развития

Добавление нового классификатора выполняется добавлением нового корневого узла.

Добавление нового производителя не требует изменения структуры БД.

Добавление нового каталога выполняется созданием новых узлов дерева.

Добавление нового пространственного объекта выполняется созданием нового узла дерева.

Добавление нового организационного объекта выполняется созданием нового узла дерева.

Изменение структуры таблиц для расширения модели не допускается.

Расширение модели должно выполняться исключительно добавлением данных.

---

# Заменяемые сущности

| Старая таблица | Новая сущность |
|---------------|----------------|
| device_types | classifiers |
| device_brands | vendors |
| device_models | catalog_items |
| buildings | space_objects |
| departments | space_objects |
| locations | space_objects |
| organizations | organization_objects |

---

# Статус

Настоящий документ считается основным описанием Master Data проекта.

Все последующие физические модели БД обязаны соответствовать настоящему документу.

# Общие правила

## Идентификаторы

Во всех таблицах используется

```
id          primaryKey()
```

Использование bigint запрещено.

---

## Иерархия

Во всех древовидных сущностях используется

```
parent_id   integer NULL
```

Если запись является корнем дерева

```
parent_id = NULL
```

---

## Программный идентификатор

```
code varchar(64) NOT NULL UNIQUE
```

Используется исключительно программной логикой.

Не отображается пользователю.

Не изменяется после создания записи.

---

## Отображаемое имя

```
name varchar(255) NOT NULL
```

Используется исключительно пользовательским интерфейсом.

Использование поля `name` в программной логике запрещено.

---

## Сортировка

```
sort_order integer NOT NULL DEFAULT 0
```

---

## Активность

```
is_active boolean NOT NULL DEFAULT TRUE
```

---

## Временные поля

```
created_at timestamp NOT NULL DEFAULT now()

updated_at timestamp NOT NULL DEFAULT now()
```

Поле `updated_at` изменяется исключительно триггером

```
update_updated_at_column()
```

---

## Стандарт внешних ключей

Во всех новых таблицах используется единый стандарт:

```
ON DELETE RESTRICT

ON UPDATE CASCADE
```

Использование иных вариантов допускается только при наличии отдельного архитектурного обоснования и должно фиксироваться в ADR.

Стандарт Yii Migration:

```php
$this->addForeignKey(
    'fk_child_parent',
    '{{%child}}',
    'parent_id',
    '{{%parent}}',
    'id',
    'RESTRICT',
    'CASCADE'
);
```

---

## Стандарт именования объектов БД

### Таблицы

Используются существительные во множественном числе.

Примеры

```

catalog_items

space_objects

organization_objects
```

---

### Первичные ключи

Не именуются явно.

Используется стандартное имя PostgreSQL по-умолчанию

Пример

```
vendors_pkey
```

---

### Внешние ключи

```
fk_<table>_<column>
```

Примеры

```

fk_space_objects_parent
```

---

### Уникальные ограничения

Также не именуются вручную.

Используется стандарт PostgreSQL:

```
<table>_<column>_key
```

---

### Индексы

Обычные

```
ix_<table>_<column>
```

---

### Триггеры

```
trg_<table>_updated_at
```

---

# Триггеры

После создания каждой новой таблицы обязательно создаётся триггер

```
BEFORE UPDATE

EXECUTE FUNCTION update_updated_at_column()
```

При удалении таблицы триггер удаляется в `safeDown()` до удаления таблицы.

---

# Правила разработки

Запрещается

- использовать `name` для поиска и программной идентификации;
- использовать `bigint` без отдельного ADR;
- изменять физическую структуру таблиц без изменения настоящего документа;
- нарушать единый порядок расположения полей.

Обязательно

- использовать `code` как программный идентификатор;
- использовать `parent_id` для всех иерархических сущностей;
- использовать единый триггер `update_updated_at_column()`;
- использовать единый стандарт внешних ключей;
- соблюдать единый стиль именования объектов БД;
- соблюдать единый стиль оформления миграций.

Каждый этап должен быть полностью завершён, протестирован и зафиксирован отдельным коммитом перед переходом к следующему.

После завершения выполнить коммит.

# Этап 8. Удаление старой структуры

Удаляются только те таблицы, которые полностью выведены из эксплуатации.

Удаление допускается только после проверки отсутствия зависимостей.

Удаление выполняется отдельными миграциями.

После завершения выполнить коммит.

---

# Общие правила

Каждая миграция должна:

- полностью соответствовать PDM-0001;
- быть атомарной;
- иметь корректный safeDown();
- создавать все необходимые индексы;
- создавать триггер `update_updated_at_column()`;
- использовать единый стандарт внешних ключей;
- быть полностью работоспособной без последующих исправлений.

---

# Правила разработки

Запрещается

- объединять несколько логических этапов в одну миграцию;
- изменять утверждённую архитектуру;
- выполнять перенос данных одновременно с созданием структуры;
- удалять старые таблицы до завершения переноса.

Обязательно

- один логический этап — одна миграция;
- один завершённый этап — один коммит;
- переходить к следующему этапу только после успешного тестирования предыдущего.

---

# 6. Mapping Specification

# Mapping Specification

Версия: 1.0

Статус: Accepted

Дата: 2026-07-22

---

# Назначение

Настоящий документ определяет правила переноса существующих справочников в новую подсистему Master Data.

Документ является обязательной инструкцией при разработке миграций переноса данных.

Создание новой структуры и перенос данных являются независимыми этапами.

Удаление старых таблиц допускается только после полного завершения переноса и перехода всех компонентов проекта на новую архитектуру.

---

# Общие правила

## Последовательность

Для каждого справочника используется единый порядок действий:

1. Создание новой структуры.
2. Создание модели ActiveRecord.
3. Перенос данных.
4. Адаптация сервисов.
5. Адаптация пользовательского интерфейса.
6. Проверка работоспособности.
7. Удаление старой структуры.

---

## Временные поля соответствия

При необходимости допускается создание временных полей соответствия.

Пример

```
legacy_id
```

Назначение

Хранение идентификатора исходной записи.

Используется исключительно на этапе миграции.

После завершения перехода временные поля удаляются отдельной миграцией.

# Карта соответствия

---

## device_types

Исходная таблица

```
device_types
```

Новая таблица

```
classifiers
```

Корневой классификатор

```
device_types
```

Перенос

Все записи становятся дочерними элементами корневого узла
`device_types`.

---

## device_brands

Исходная таблица

```
device_brands
```

Новая таблица

```
vendors
```

Перенос

Каждый производитель создаётся как самостоятельная запись.

Иерархия отсутствует.

---

## device_models

Исходная таблица

```
device_models
```

Новая таблица

```
catalog_items
```

Перенос

Модели становятся элементами каталога.

Родитель определяется структурой каталога.

Связь с производителем осуществляется через `vendor_id`.

---

## buildings

Исходная таблица

```
buildings
```

Новая таблица

```
space_objects
```

Тип объекта

```
building
```

Перенос

Каждое здание становится корневым пространственным объектом.

---

## departments

Исходная таблица

```
departments
```

Новая таблица

```
space_objects
```

Тип объекта

```
block
```

или иной тип согласно классификатору пространственных объектов.

Перенос

Подразделения размещаются внутри соответствующего здания.

Итоговая иерархия определяется пространственной моделью предприятия.

---

## locations

Исходная таблица

```
locations
```

Новая таблица

```
space_objects
```

Тип объекта

Определяется классификатором.

Например

```
floor

room

workplace
```

Перенос

Объекты включаются в соответствующую пространственную иерархию.

---

## organizations

Исходная таблица

```
organizations
```

Новая таблица

```
organization_objects
```

Тип объекта

```
organization
```

Перенос

Организации становятся корневыми элементами организационной структуры.

---

# Таблицы, не участвующие в переносе

Настоящий этап не затрагивает

```
devices

employees

movements

users

printer_page_counters

discovered_devices

...
```

Они будут адаптироваться после завершения формирования новой Master Data.

---

# Порядок удаления старых таблиц

Удаление допускается только после выполнения всех условий:

- данные полностью перенесены;
- ActiveRecord переведены;
- сервисы используют новую структуру;
- API использует новую структуру;
- Discovery использует новую структуру;
- пользовательский интерфейс использует новую структуру;
- отсутствуют ссылки на старые таблицы.

Удаление выполняется отдельными миграциями.

---

# Контроль завершения

Рефакторинг считается завершённым после выполнения следующих условий:

- все новые таблицы созданы;
- все справочники перенесены;
- все сервисы используют новую структуру;
- все модели используют новую структуру;
- старые таблицы удалены;
- временные поля соответствия удалены;
- документация актуализирована.
